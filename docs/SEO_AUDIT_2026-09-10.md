A second full pass over brollyjuniors.com, one day after
[SEO_AUDIT_2026-09.md](SEO_AUDIT_2026-09.md). That document remains accurate
and is not superseded; this one records what changed, what it missed, and what
could be measured this time that could not be measured then.

Companion documents: [SEARCH_DEMAND_2026-09.md](SEARCH_DEMAND_2026-09.md) (the
first real keyword data this repository has had) and
[SEO_STRATEGY.md](../SEO_STRATEGY.md).

## 1. Executive summary

**The September 9 fixes were deployed and they worked.** `npm run verify:deploy`
against production reported 12 failures that day; the same checks pass now. The
canonical URLs answer 200, unknown URLs 404, the legacy 301s fire, `www` and
`http` redirect. That was the right call and it is done.

**But the deploy that fixed those faults shipped a new one, and every check in
the repository passed while it did.**

24 pages — the entire `/programs/<topic>` catalogue — were being **301-redirected
away in production**. They are prerendered, in the sitemap, in the mega menu,
and internally linked. `/programs/coding` redirected to `/python-for-kids`; the
other 23 redirected to `/programs`.

The cause is a legacy redirect block written when the assumption in its own
comment was true:

```nginx
# No real route lives under /programs/ — only /programs itself —
# so the catch-all cannot shadow a live page.
rewrite ^/programs/(python|coding)[^/]*$  /python-for-kids  permanent;
rewrite ^/programs/.+$                    /programs         permanent;
```

The programme catalogue was added later. An nginx server-level `rewrite` runs
*before* `try_files`, so the redirect won every time, and the prerendered page
was never reached. This is the same class of fault as F1 in the previous audit —
a canonical sitemap URL that answers 301 — reintroduced by a different
mechanism, on 12% of the site.

It survived because **every existing check looked at the wrong thing**:
`audit:seo` verified that redirect *targets* exist but never that a redirect
*source* collides with a real page, and `verify:deploy` sampled four canonical
URLs out of 204 — none of them under `/programs/`.

Both gaps are now closed by checks, not just by the fix (§3).

**Second fault, found via the new keyword data:** every page answered 200 at
both `/path` and `/path/`. The canonical tag named the slash-free form, and
Semrush shows Google had indexed
`/resources/cbse-ai-curriculum-class-9-explained/` — **the slashed one** — in
preference to it. A canonical is a hint; the duplicate was real and Google
resolved it the wrong way.

**Content:** 195 of 346 "quick answers" (56%) restated an FAQ a few hundred
pixels above them on the same page. Now filtered at render.

**Unchanged and still the highest-value action available:** the Google Business
Profile. The demand data now quantifies it — `phonics classes near me` is
14,800 searches/month and `abacus classes near me` 8,100, against 320 for
`abacus classes in hyderabad`. No on-page work reaches a Local Pack.

## 2. Faults found

### F8 — 24 sitemap URLs 301'd away in production · **fixed in repo, needs deploy**

Measured against `https://brollyjuniors.com`, all 204 sitemap URLs:

```
checked 204 sitemap URLs
non-200: 24
  301  /programs/brain-games          ->  /programs
  301  /programs/chess                ->  /programs
  301  /programs/coding               ->  /python-for-kids
  … 21 more, all under /programs/
```

**Fix.** The legacy rules cannot run in the server block, because a rewrite
there pre-empts `try_files`. They now run only as a fallback, after nginx has
looked for a real page:

```nginx
location ^~ /programs/ {
    try_files $uri $uri/index.html @programs_legacy;
}

location @programs_legacy {
    rewrite ^/programs/abacus[^/]*$  /junior-skills/abacus  permanent;
    …
    rewrite ^/programs/.+$           /programs              permanent;
    return 404;
}
```

A prerendered page now wins; only a slug with no page of its own reaches the
redirects. The retired WordPress URLs still 301 exactly as before.

`public/.htaccess` had the identical bug in Apache form: its catch-all carried
`RewriteCond %{REQUEST_FILENAME} !-f/!-d` guards but the seven keyword-prefix
rules above it did not. All seven are now guarded.

**Verified locally**, since no nginx binary or Docker daemon was available —
`scripts/serve-like-nginx.mjs` reimplements the serving rules and was run
against the real `dist/`:

| URL | Result |
|---|---|
| `/programs/coding` | **200** (was 301 → `/python-for-kids`) |
| `/programs/chess` | **200** (was 301 → `/programs`) |
| `/programs/abacus-classes-hyderabad` | 301 → `/junior-skills/abacus` (unchanged) |
| `/programs/some-old-slug` | 301 → `/programs` (unchanged) |
| `/nope` | 404 (unchanged) |

### F9 — Every page reachable at two URLs · **fixed in repo, needs deploy**

`/programs` and `/programs/` both returned 200. Section 5 of `nginx.conf`
deliberately serves `$uri/index.html` without a redirect — correct, and the fix
for F1 — but it did the same for the slashed form.

This is not theoretical. From `resource_organic` (Semrush, India, 10 Sep 2026):

| Keyword | Position | Ranking URL |
|---|--:|---|
| cbse ai curriculum | 64 | `…/cbse-ai-curriculum-class-9-explained/` ← **slashed** |

Google chose the variant the site does *not* declare canonical.

**Fix**, at the top of the server block:

```nginx
rewrite ^(/.+)/$ $1 permanent;
```

`^(/.+)/$` cannot match `/`, so the root keeps its slash. Verified locally:
`/programs/` → 301 → `/programs`, `/junior-skills/abacus/` → 301 →
`/junior-skills/abacus`.

### F10 — 56% of "quick answers" duplicated an FAQ on the same page · **fixed and verified**

Nineteen page components each hand-rolled a "Quick answers" band directly below
the FAQ list. Measured across the built site:

```
195 / 346 quick answers duplicate an FAQ on the same page (56%), across 43 pages
```

On eleven pages every single one did. `/junior-skills/abacus` had 20 FAQs
followed by 6 quick answers, all 6 restating one of the 20 — "What age is best
to start abacus?" against "What is the best age to start abacus?".

Google's helpful-content guidance names this pattern; it also gives a retrieval
system two competing passages to cite for one question, which is the opposite of
what the GEO work on these pages is for.

**Fix.** A shared `<QuickAnswers>` component (`src/components/Shared.jsx`)
replaces all 19 hand-rolled blocks and filters its list through
`distinctQuickAnswers()` (`src/lib/faqs.js`). The FAQ copy is the fuller of the
two and is what the `FAQPage` schema emits, so the FAQ stays and the duplicate
quick answer goes. The section removes itself when nothing distinct is left.

Filtered at render rather than edited out of the data, because the same question
is worded differently in 19 files and a rule that runs every build also covers
whatever is written next.

**The 0.7 threshold was measured, not chosen.** Across the 230 quick answers on
catalogue pages, scores cluster and the band just below 0.7 sits almost entirely
at 0.67, where genuine duplicates ("Why is Biology important for children?" /
"Why should children learn Biology?") are mixed with pairs that only look alike
("Do children need to be good at drawing to join?" / "How can drawing help
children?"; "What do children learn in yoga?" / "What age can children start
yoga?"). Dropping to 0.65 would remove 27 more, including those. Deleting a
question a parent actually asked is worse than leaving a near-duplicate, so the
threshold sits where the two classes separate cleanly. Roughly a dozen
0.67-scoring duplicates survive; they are better edited in the source data.

Result:

```
before:  346 quick answers across 43 pages, 195 duplicating an FAQ
after:   151 quick answers across 40 pages,  16 duplicating an FAQ
```

No FAQ was removed, no `FAQPage` schema changed, and no unique answer was lost —
only restatements of an answer already on the page.

### F11 — The JavaScript bundle grew 55% unnoticed · **guard added; the fix is not safe to do blind**

The September 9 audit measured `content-data` at 915 KB and recorded route-level
code splitting as the fix. One day and one feature branch later:

| Chunk | Size |
|---|--:|
| `content-data` | **1,399 KB** (was 915 KB) |
| `index` (app code) | 818 KB |
| `react` | 139 KB |
| `router` | 22 KB |
| **Total** | **2,378 KB** |

Nothing was watching, so it grew silently. That is the part I fixed: `audit:seo`
now warns past a budget of 2,600 KB total / 1,500 KB largest chunk. Proved to
fire by temporarily lowering the budget to 2,000/1,000, which produced both
warnings, then restoring it.

**I did not do the route-level split, and I want to be precise about why.**
`src/data/catalog/index.js` merges the full `detail` body from
`programmeDetails.js` (426 KB) and `tuitionDetails.js` (676 KB) into
`catalogPages`, and that same array feeds the route manifest, the sitemap, the
prerenderer, `lib/faqs.js` (which sources `FAQPage` schema from `detail.faqs`)
and `lib/seo.js`. Splitting the bodies out means restructuring all of that,
across SSR and client, where a hydration regression is a visible production bug.
The brief's own standard — "avoid broad rewrites that add risk without
measurable benefit" — argues against doing it in the same pass as the routing
fixes.

It is also worth being honest about the size of the prize. Every page is
prerendered and the bundle is `type="module"`, so this does **not** block LCP;
content paints without it. The cost is hydration time and mobile data. With the
site at zero organic traffic, discovery is the binding constraint, not INP. This
is real work, but it is not the next work. Staged plan in §8.

## 3. The checks that let F8 through, and what replaced them

A fix without a check just waits to be reintroduced. Both gaps are now covered,
and **both new checks were proved by injecting the real fault and confirming a
failure**, then reverting — a check that silently does not run reports "no
problems" exactly like a check that passes.

### 3.1 `audit:seo` — redirect shadowing (build time)

The existing check asked whether each redirect *target* resolves. The new one
asks the reverse: does any redirect *source pattern* match a URL in the sitemap?

It has to track context or it flags the very arrangement that fixes the bug — an
nginx server-level `rewrite` shadows, one inside a `location` reached through a
`try_files` fallback does not, and neither does an Apache rule guarded by
`!-f`/`!-d`. So it parses brace depth for nginx and `RewriteCond` state for
Apache.

Proof, with the fault reinstated:

```
✗ nginx.conf — redirect ^/programs/(python|coding)[^/]*$ -> /python-for-kids
  shadows /programs/coding, which is a real page in the sitemap
✗ .htaccess  — redirect ^programs/(python|coding)[^/]*$  -> /python-for-kids
  shadows /programs/coding, which is a real page in the sitemap
```

### 3.2 `verify:deploy` — every sitemap URL (deploy time)

It sampled 4 of 204, on the stated reasoning that "204 requests to prove one
server rule is rude". That reasoning is what let 24 broken pages sit in
production: a rule that applies per URL pattern has to be checked per URL, and
these are HEAD requests against a static nginx.

It now checks all of them, 8 in flight, and lists the broken ones in full
because the *pattern* of which URLs broke is what identifies the rule at fault.
`--sample` restores the old spot check. A trailing-slash duplicate check was
added alongside (F9).

Against production right now — this is the acceptance test for the deploy:

```
✗ all 203 sitemap URLs return 200 — 24 do not: /programs/brain-games -> 301 /programs;
  /programs/chess -> 301 /programs; /programs/coding -> 301 /python-for-kids; …
✗ trailing-slash URLs redirect (25 sampled) — 25 answer 200 at both /path and /path/
```

Both must go green after deploying.

### 3.3 Proof that the fix clears them

The same verifier, run against `scripts/serve-like-nginx.mjs` serving the real
`dist/` under the corrected rules:

```
✓ all 203 sitemap URLs return 200
✓ trailing-slash URLs redirect (25 sampled)
✓ unknown URL returns 404
```

Both failures pass. The six failures that remain in that local run —
the legacy `.html` redirects, gzip and cache headers — are sections of
`nginx.conf` the stand-in deliberately does not implement (it mirrors only the
serving rules, §0/3a/5), and all six are already confirmed working on
production. They are an artefact of the harness, not of the config.

## 5. GEO / AEO / AIO

Unchanged from the previous audit and still the site's real strength: 204
prerendered pages, answer-first openings, a valid entity graph, and the 90
module pages that no local competitor matches.

F10 is the substantive change here, and it is a GEO improvement rather than a
cosmetic one. Two passages answering the same question in two lengths on one
page is worse for a retrieval system than one good passage: it splits the
citation and neither version is clearly authoritative. Removing 195 restatements
leaves the fuller FAQ answer — the one already in `FAQPage` schema — as the
single thing to cite.

The honest limitation is also unchanged: almost no first-hand evidence a model
can cite. No original data, no photographs of the centre, no named educator with
verifiable credentials. That needs facts, not code (§7).

## 6. Keyword and intent

Fully covered in [SEARCH_DEMAND_2026-09.md](SEARCH_DEMAND_2026-09.md). The three
findings that matter:

1. **The site has 3 ranking keywords and 0 organic traffic in India.** It is
   pre-visibility, not underperforming. Crawl integrity and local presence beat
   keyword tuning at this stage — which is what makes F8 the most expensive item
   in this document.
2. **Several declared keyword contracts target zero-volume phrases** —
   `coding classes for kids in hyderabad` and
   `public speaking classes for kids in hyderabad` both measure 0/month. The
   public-speaking page nonetheless ranks 41st for
   `public speaking classes for kids` (210/mo), the term it was never aimed at.
   This is not an argument to rewrite the titles; "in Hyderabad" is right for a
   single-centre business. It is an argument that the `keyword` field in
   `seo.js` is a *placement contract*, not a demand estimate, and should not be
   read as one.
3. **The demand is overwhelmingly local and sits in the Local Pack** —
   `phonics classes near me` 14,800/mo, `abacus classes near me` 8,100/mo,
   against 320 for `abacus classes in hyderabad`. This is the arithmetic behind
   the GBP recommendation.

The best on-page opportunities the site can serve truthfully today, needing no
new pages: `robotics classes for kids` (720/mo, **KD 9** — the lowest-difficulty
term with real volume anywhere in the data, and `/programs/robotics` was one of
the 24 pages being redirected away), `abacus online classes` (4,400, KD 18 — the
abacus page already has an "Online abacus classes" section), and
`vedic maths classes` (3,600, KD 22).

**No new page is recommended for any of them.** Each is an intent an existing
page already serves, and a page per keyword variation is the doorway pattern
Google's spam policies name explicitly.

## 8. Remaining dependencies and risks

### Requires a deploy

1. **Deploy `nginx.conf`**, then `npm run verify:deploy`. Both current failures
   must clear: 24 pages returning 200, and the trailing-slash check. Run
   `nginx -t` first (§7).

### Requires business facts I will not invent

2. **Google Business Profile.** Still not linked, so presumably still not
   verified. The demand data now sizes it: ~23,000 monthly "near me" searches
   across abacus and phonics alone, none reachable without it.
   [GBP_SETUP.md](GBP_SETUP.md), [REVIEWS_PLAYBOOK.md](REVIEWS_PLAYBOOK.md).
3. **`src/data/site.js` blanks** — `latitude`/`longitude` are `null`,
   `mapEmbedSrc`/`placeUrl`/`reviewUrl` empty, all seven `socialProfiles` empty.
   Correctly omitted rather than guessed, but they are the `sameAs` signals that
   tie the site to the Business Profile.
4. **Named educators and photographs of the centre.** The strongest E-E-A-T gap
   and the main reason there is nothing first-hand for a model to cite.

### Requires access I do not have

5. **Search Console.** Still the only source for positions 4–20, CTR outliers,
   cannibalisation and indexing exclusions.
6. **Semrush API units** (exhausted) and **Ahrefs** (`Insufficient plan`).

### Risks

- **The `/programs/` fault will recur if the check is removed.** It is the only
  thing standing between a new catalogue route and a silent 301. The redirect
  patterns are deliberately broad, and that is why.
- **The `.htaccess`/`nginx.conf` split is still a standing trap** — two files
  must agree, and this pass had to fix the same bug twice. If Apache is retired,
  deleting `public/.htaccess` is safer than maintaining both. **Your call; I
  have not deleted it.**
- **`scripts/sitemap-dates.json` must stay committed**, or the next build
  re-dates all 204 URLs.
- **The JS budget is a ceiling, not a fix.** It will warn at the next 200 KB. It
  will not make the page lighter.
